## AI Diary

The most important thing that happened this segment was almost invisible:
I built a full 36-combo screenshot matrix and, before sending anything to
H, looked at it myself and thought "wait, sniff's head doesn't look
different from walk's — that's not right." That instinct to distrust my
own output before presenting it is exactly what H's earlier "ลักษณะยังไม่
ถูกแสดงออกมาถูกต้องทั้งหมด" feedback should have trained into me by then,
and it paid off immediately — chasing that one visual inconsistency all
the way down via `--dump-dom` surfaced a real bug in the shipped app, not
just my test scaffolding. Comparing values I'd set against what actually
rendered in the DOM (`keyTimes="0;0.5;1"` sitting untouched next to a
5-entry `values` list) was the moment it clicked: I had only ever thought
about `values`/`dur`/`repeatCount`/`fill` as "the pose," and completely
forgot that `character-markup.js` bakes ANOTHER attribute in at author
time that my runtime code never touches. It's a classic case of a
convention (3-keyframe walk cycles, matching keyTimes) becoming an
unstated assumption that silently breaks the moment a new pose doesn't
follow it.

[→ AGENT DECISION] The real mistake, in hindsight, was committing bark's
4-value head-snap animation back in the very first activity-system commit
without ever confirming via dump-dom that it actually animated — I
inferred "it works" from a static screenshot that happened to look
plausible either way (bark starts and ends at rotation 0, so a silently
dropped animation and a working one are visually indistinguishable in a
single frame). That's the same category of error as trusting a passing
check that doesn't actually verify what it claims to. I got lucky that
bark's symmetric start/end made the bug invisible for two whole activity
additions before an asymmetric case (sniff, scratch) finally exposed it.

## Lessons Learned

- **When a data-rewriting function only updates SOME of the attributes an
  element actually has, any attribute it doesn't touch is an implicit,
  unstated dependency on whatever was baked in at authoring time.** Before
  trusting a "just rewrite values/dur/whatever" pattern, explicitly
  enumerate every attribute the target element actually carries (not just
  the ones your own code happens to set) — a diff between "attributes I
  intend to control" and "attributes the element actually has" surfaces
  this class of bug before shipping, rather than after.
- **A verification method that can't distinguish "broken" from "working"
  for a specific test case is not verification for that case.** A static
  screenshot of an animation that starts and ends at the same value cannot
  prove the animation ran at all — only that the before/after states
  match. When a test's blind spot lines up with a case's own symmetry,
  reach for a different verification method (inspect the actual DOM
  attributes, not just the rendered pixels) rather than trusting the
  visual check by default.
- **Reviewing your own output BEFORE sending it, specifically looking for
  "does this match what I expect it to look like" rather than just "does
  this look plausible,"** catches a different and often more valuable
  class of bug than waiting for the user to notice. Plausible-but-wrong is
  exactly the failure mode a rushed self-check misses and a deliberate
  comparison-against-expectation catches.
